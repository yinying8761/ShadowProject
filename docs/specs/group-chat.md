# 群聊（Group Chat）+ 时间戳对话记录

> 日期：2026-09-21 | 状态：待实现 | 来源：`想法保留库.md` #13（群聊，AI 可以互相聊天）+ 2026-09-21 grilling 定稿

本 spec 分两个阶段交付，**Phase 1 先落地、Phase 2 再上群聊**：

- **Phase 1 — 时间戳对话记录**：AI 看到的对话记录带上「时间 + 说话人」，用户打开历史记录也能看到；1:1 立即受益，同时为群聊的「谁说了什么」铺好数据与渲染。
- **Phase 2 — 群聊**：一个会话里有多个角色，用户发言后角色按序回应、可互相接话，可跳过、可续说；群聊有自己的对话列表、记忆与 compact。

## Problem Statement

1. **AI 没有时间感**：喂给 LLM 的对话历史只有 `{role, content}`，没有时间戳——角色不知道「上次聊天是三天前」「你这句话是昨天说的」，容易把旧事当新鲜事，也无法自然地提起时间跨度。
2. **历史记录看不到时间与说话人**：用户翻历史只能看到一条条消息，不知道每条是什么时候说的；群聊场景下更无法分辨「这句话是谁说的」。
3. **没有群聊**：现在一个会话只能属于一个角色（`Conversation.character_id` 非空），用户无法让多个角色同处一室、互相聊天——这是想法库里明确想要的能力（#13）。
4. **群聊不是"多开一个窗口"**：多角色同场需要解决「谁在什么时候说话、说几句就停、用户插话怎么办、多个角色的记忆与摘要怎么算」等一连串语义问题；不定清楚就会变成烧 token 的失控聊天或记忆污染。

## Solution

**Phase 1 — 时间戳对话记录**

- 新增统一的**对话记录渲染**：每条文本消息渲染为 `2026/9/20 14:25 [说话人]: 内容`（系统本地时区）。
- 同一条渲染规则服务两个消费者：**喂给 LLM 的上下文** 与 **用户打开的历史记录**。
- 聊天气泡**不变**（不在气泡内联时间戳）；历史记录视图展示带时间与说话人的格式。
- 说话人：用户消息 → 用户画像里的名字（缺省「用户」）；1:1 的 AI 消息 → 该会话角色名；群聊的 AI 消息 → 该条消息的发言角色。

**Phase 2 — 群聊**

- **群** 是固定角色集合 + 共享对话流；一个群可以开**多条对话**（和 1:1 一样有对话列表、自动命名、新对话按钮）。
- 用户发言后，群成员**按顺序依次**决定「要不要回话」「要不要继续说」；角色之间可以互相接话（B 评论 A）——但每轮都锚定在用户发言上，不做无锚点的后台自治聊天。
- 每个「用户轮」有**链预算**（角色消息总量上限，默认 6 条）：到顶或全体跳过即静默，等用户下一句。
- 用户可在角色思考时继续发言：**不打断在途回复**，等本轮收尾后新消息作为**新的一轮**（预算重置）接力。
- 打开群聊时后台补账：**先提取记忆、后 compact**；跨多日再打开时按窗口日期一次性补齐，记忆时间用消息真实日期。
- 群聊**禁用每日问候与主动说话**、**禁用 TTS**（预留回归开关）。

## User Stories

### Phase 1 — 时间戳对话记录

1. 作为用户，我想让角色知道「这句话是什么时候说的」，so that 它能自然提起时间跨度（"你三天前说…"）而不是把旧事当新鲜事。
2. 作为用户，我想在历史记录里看到每条消息的时间，so that 我翻记录时能回忆起当时的语境。
3. 作为用户，我想在历史记录里看到每条消息的说话人，so that 群聊时我能分清是谁说的。
4. 作为用户，我不想聊天气泡被时间戳弄乱，so that 正常聊天界面保持干净。
5. 作为用户，我想时间戳用我本机的时间，so that 和我看到的一切时间一致。
6. 作为开发者，我想「喂 LLM 的记录」和「历史记录展示」共用同一套渲染，so that 两处永远不会不一致。
7. 作为开发者，我想渲染是一个不碰数据库的纯函数，so that 我能直接单测各种格式边界（跨天、tool 消息、无名用户）。

### Phase 2 — 群聊

8. 作为用户，我想创建群聊（起名 + 选成员），so that 我能把几个角色放进同一个房间。
9. 作为用户，我想在设置面板里看到我建过的所有群并能点进去，so that 管理入口集中、不用在聊天里翻。
10. 作为用户，我想编辑群（改名、增删成员），so that 群能随我的需要变化。
11. 作为用户，我在群里说一句话后，想看到成员们依次回应，so that 像真的多人聊天。
12. 作为用户，我想让角色之间互相接话（B 吐槽 A 的观点），so that 群里是真正的交流而不是各答各的。
13. 作为用户，我想让无话可说的角色保持沉默，so that 群里不会每个人都硬凑一句。
14. 作为用户，我想让角色能接着说（不只一句），so that 表达完整。
15. 作为用户，我不想群里无限刷屏，so that token 消耗与信息量都可控（每轮有上限）。
16. 作为用户，当我在角色思考时又发了一句，我想它不打断当前回复、并在本轮结束后接着处理我的话，so that 体验连贯、不丢字。
17. 作为用户，我想群聊也能开新对话，so that 长群聊不会因为注意力涣散让角色变笨。
18. 作为用户，我想群聊对话也有自动标题，so that 侧边栏里分得清每一段群聊。
19. 作为用户，我想群聊里每个角色用它自己的记忆，so that 它记得的是和我之间的历史。
20. 作为用户，我隔几天再打开群聊时，想让它补上这几天该记的事和摘要，so that 角色不会"失忆"。
21. 作为用户，我想群聊里的记忆时间对应消息真实发生的时间，so that 角色回忆时不把三天前说成今天。
22. 作为用户，我想群聊里角色也能用工具（查资料、记忆、看时间），so that 它们在群里的发言不是空口白话。
23. 作为用户，我不想群聊里突然响起角色们的语音（现在的 TTS 会重叠、很吵），so that 群聊安静可控；将来 TTS 好了能再打开。
24. 作为用户，我不想群里突然收到每日问候或主动搭话，so that 群聊只在我想聊的时候动。
25. 作为用户，我想群聊用完整模式（有成员列表与对话列表），so that 布局信息量够用。
26. 作为开发者，我想群轮的编排逻辑独立于数据库与网络，so that 我能用假对象测出「顺序/跳过/预算/插话新轮」全部语义。
27. 作为开发者，我想群聊复用现有的 Agent（每角色一实例）、工具运行时、记忆提取与 compact，so that 不引入第二套机制。

## Implementation Decisions

### Phase 1 — 时间戳对话记录

- **统一渲染器**（新模块，纯函数）：消息列表 → 文本行 `2026/9/20 14:25 [说话人]: 内容`。
  - 时间：`Message.created_at` 按**系统本地时区**渲染；格式显式拼接 `年/月/日 时:分`（月/日不补零；**Windows 的 strftime 不支持 `%-m`/`%-d`**，不能直接用它）。
  - 说话人：用户消息 → 用户画像的 `user_name`（缺省「用户」）；1:1 的 AI 消息 → 该会话的角色名；群聊 AI 消息 → 该消息的发言角色名。
  - 仅 **user/assistant 文本消息**加前缀；`tool` 角色消息与工具调用载体**不加**。
- **消费者**：① 喂 LLM 的上下文组装；② 历史记录接口与前端历史视图。两者调用同一渲染器，禁止各写一份。
- 聊天气泡不变；流式过程中不显示时间戳。
- `Message` 新增 **`speaker_id`**（可空）：群聊里记录发言角色；1:1 保持空（说话人由会话角色派生）。可空列，走增量迁移。

### Phase 2 — 群聊

#### 群实体与数据模型

- 新增 **群**（`Group`）：名称 + 创建时间。
- 新增 **群成员**（`GroupMember`）：群、角色、**发言顺序**。
- `Conversation` 新增 **`group_id`**（可空）：有值即群对话；并新增 **`last_extract_at`**（可空）作为"打开时补账"的锚点。
- `Conversation.character_id` 需变为**可空**（群对话没有单一角色）。SQLite 不能直接改列约束 → **一次性重建式迁移**（建新表→拷数据→换名），偏离项目现有的"只加列"惯例，需显式迁移脚本与备份；**建议同时落一个 ADR**记录这次约束变更。
- 1:1 语义不变：`group_id` 为空的会话行为与现在完全一致。

#### 群轮编排

- **串行**：一次只跑一个角色的一轮（一个 LLM 流），永不并行。
- **顺序**：按成员 `position` 依次。
- **每角色的三种输出**：
  - **跳过**：提示词约定「无话可说时只输出 `<silent>`」；编排器识别后**丢弃**（不落库、不推送）；
  - **一条消息**：落库（`speaker_id` = 该角色）并推给前端；
  - **继续说**：同一角色再生成一条（仍计入链预算）。
- **链预算**：每个「用户轮」角色消息总量上限 **6**（常量、可配）。到顶 → 整群静默；**全体跳过** → 本轮静默结束。
- **插话语义**：群轮在途时用户又发消息 → 不打断在途流；当前角色本轮收尾后，**旧轮立即收束**（不再让剩余成员就旧消息发言），队列中的用户消息**合并为一个新轮**（预算重置）接力；旧消息仍在历史中。
- **绝缘**：群对话不启动主动陪伴会话、不响应每日问候。
- 每角色的上下文 = 完整群记录（时间戳格式）+ 该角色人设 + 该角色记忆 + 全量工具。

#### 群记忆与 compact

- **触发**：打开群对话时启动**后台任务**（不阻塞聊天），同一对话有 in-flight 去重。
- **顺序固定：先提取 → 后 compact**（交换顺序会丢内容）。
- **提取**：一次 LLM 提取（提示词硬性限定「只提取关于用户的持久事实，不提取任何角色的观点或群内对话过程」）→ **同一批事实存储 N 份**（每个成员各一份，`character_id` = 成员），记忆时间用**消息真实日期**。
- **补账**：锚点 = `Conversation.last_extract_at`；隔数日再打开时一次性处理该窗口内的全部内容。
- **compact**：复用现有摘要 + 裁剪；群对话的摘要输入同样走时间戳渲染（保留"谁说了什么"）。

#### 前端

- 设置面板左栏新增**「群聊」**项：右侧展示已创建群列表 + 「创建群聊」（起名 + 选成员）；点击群名进入该群聊。
- 群聊**强制完整模式**；从紧凑模式进入则切换，退出群聊回单聊时恢复进入前的模式。
- 群聊窗口：**左上角成员列表**；**左侧栏**为对话记录标题（该群的对话列表）；**左下角**「新对话」按钮。
- 群内消息按说话人区分（名字 + 视觉标识）。
- **TTS 在群聊禁用**（见 Out of Scope），但保留开关/挂钩以便将来回归。
- 历史记录视图展示 `时间 [说话人]: 内容`。

## Testing Decisions

原则：只测外部行为，不测内部写法；优先复用现有缝；前端手工验收。

|---|---|---|---|

| **S2 历史记录接口** | 现有 REST + `TestClient` | 历史消息返回时间戳与说话人 | `test_conversation_title.py`、`test_tool_runtime.py` 的 client 模式 |
| **S3 群轮编排器**（新建，纯逻辑） | 注入「跑一个角色一轮」的可调用对象 + 假时钟；不碰 DB/网络 | 串行顺序、跳过不落库、链预算 6 封顶、全体跳过静默、插话→旧轮收束+新轮预算重置、在途不打断 | `test_circuit_breaker.py`（纯类注入 fakes） |

| 前端（设置面板群聊项、群窗口、成员列表、历史视图） | 项目无前端测试基建 | 手工验收 | — |

- 回归：全量 `python -m pytest tests/ -v`。
- 1:1 回归重点：渲染器接入后 1:1 的 LLM 上下文与历史记录行为变化必须是**纯增量**（内容前缀）而不改变任何既有语义。

## Out of Scope

- **无锚点的 AI 自治群聊**（角色在后台自己聊、用户纯旁观）——本版只做用户驱动。
- **群成员规模上限**——暂不设限（全员依次回应的成本随人数线性上升，将来按实测再定）。
- **群聊 TTS**——因现有 TTS 有延迟、会出现多角色语音重叠；预留开关，等串行语音队列或更好的 TTS 再加回。
- **按发言人归属的记忆提取**（提取时按说话人切分归属）——将来若出现记忆污染再升级。
- **群共享记忆池**（跨角色的群记忆）——与"记忆按角色隔离"冲突，需单独设计。
- **@ 指定角色发言**——本版用户发言默认面向全体，由角色自行决定是否回应。
- **成员实时进出**——只支持「编辑群」（管理操作），不支持聊天中实时加入。
- **紧凑模式下的群聊界面**——群聊强制完整模式。
- 角色立绘/表情（想法库 #5）、完全关闭窗口（#3）、主动回复通知完善（#4）、顶栏配色适配（#8）、更换新 TTS（#14）——均不在本 spec。

## Further Notes

- **实施顺序**：Phase 1（时间戳对话记录）先交付并可独立验收；Phase 2 依赖 Phase 1 的渲染器与 `speaker_id`。建议按 S1→S2（Phase 1）→ S5→S3→S4→前端（Phase 2）推进。
- **想法库映射**：本 spec 覆盖 #13（群聊）；#11（内置小游戏、AI 可操控）与 #12（AI 操作电脑软件）是后续独立方向。
- **建议 ADR**：`conversations.character_id` 由非空改为可空需要重建式迁移，偏离项目"只加列"惯例——值得一个 ADR 记录该约束变更与"群对话无单一角色"的模型决定。
- **成本**：时间戳前缀约每条消息 +20~30 token（可忽略）；群聊每用户轮最多 6 条角色消息 × (人设 + 完整群记录 + 工具定义)，是本功能的主要成本来源，链预算即是它的闸门。
- **术语**：本 spec 新增/固化的领域词（群、群聊、发言者、链预算、时间戳对话记录）已补入 `CONTEXT.md` 术语表。
