## ⚠️ 2026-11-09 修正：R04–R07 改判为「环境噪声」

最初把 R04–R07 归为「疑似 harness 判定错」（理由是四例同为 `run, tools, answer` 三连挂）。**经验证，这个归类是错的。**

硬对账：

- `eval/faults.py` 的注入信封只有四种，字样固定：
  - `error` → `{"error": "<tool> failed: injected fault (eval)"}`
  - `timeout` → `{"error": "Timeout after 30s"}`
  - `circuit_open` → `{"error": "Circuit breaker open for <tool>"}`
  - `empty` → `""`
- 而 R04–R07 的实际错误是 **`Connection error.`** 与 **`Request timed out.`**——**两种都不在注入信封里**，字面也不匹配。它们是 LLM API / httpx 的连接层错误：那一轮根本没跑到工具调用就被打断，于是 `run` 判负连带 `tools` / `answer` 一起挂。

**教训**：如果照原计划去"修判定"，会把一个正常的 `run` 判负改成不出声，**反而掩盖真实的运行失败**。先定性、再动手，比"看着像就改"重要。

## 结论一句话（修正后）

8 个失败里**没有一个是产品功能性 bug 的直接证据**：**4 个环境噪声**（R04–R07）、1 个断言过窄（S03）、1 个预算口径可疑（R01）、2 个待人工读输出（T03/V01）。

但也不要过度乐观：**恢复能力（Failure Recovery）的真实水平仍未测出**——4 个环境噪声刚好落在 recovery 层，所以「2/7」这个数字目前不可信，需在网络正常时重跑该子集。

## 横向结论

1. **R04–R07 同因但不是代码问题**：同一轮网络抖动连续打断四个用例；改 harness 是错的。
2. **最该先做的是"在网络正常时重跑 recovery 子集"**，把真实恢复能力测出来；在此之前不要根据 2/7 做任何结论。
3. **可复现性风险**：这轮跑在 11-04（当时网络可用）。本机 SOCKS 代理（`127.0.0.1:7890`）一度不可用；recovery / 搜索类用例依赖网络，**网络条件不同则失败集不同**，对比基线前必须确认网络一致。

## 待定：基础设施失败应与行为失败分开记账（只建议，未实施）

即便是真实网络错误，把整个 case 判成 `run` 失败也会污染质量信号。按 ADR-0012 的精神，基础设施失败应当单独标记（例如 `not_run` / `infra_error`）并在汇总里单列，**不进通过率分母**。

这会扩大 eval 的判定语义（新增一种"没跑成"的状态），超出"修 R04–R07"的范围，因此本轮未做。要做得单独立项（改 ADR-0012 或加一条）。

## 为什么这张表要入库

`backend/eval_results.md` 是每次跑都会变的生成物，故意不入库。但它是这张表唯一的依据——若不把判断固化下来，将来没人能追溯"8 条失败为什么这样归类"。所以本文件入库，并在 `docs/STATE.md` §4 引用。
