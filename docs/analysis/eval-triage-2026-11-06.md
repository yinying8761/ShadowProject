## ⚠️ 2026-11-09 修正：R04–R07 改判为「环境噪声」

最初把 R04–R07 归为「疑似 harness 判定错」（理由是四例同为 `run, tools, answer` 三连挂）。**经验证，这个归类是错的。**

硬对账：

- `eval/faults.py` 的注入信封只有四种，字样固定：
  - `error` → `{"error": "<tool> failed: injected fault (eval)"}`
  - `timeout` → `{"error": "Timeout after 30s"}`
  - `circuit_open` → `{"error": "Circuit breaker open for <tool>"}`
  - `empty` → `""`
- 而 R04–R07 的实际错误是 **`Connection error.`** 与 **`Request timed out.`**——**两种都不在注入信封里**，字面也不匹配。它们是 LLM API / httpx 的连接层错误：那一轮根本没跑到工具调用就被打断，于是 `run` 判负连带 `tools` / `answer` 一起挂。

**教训**：如果照原计划去"修判定"，会把一个正常的 `run` 判负改成不出声，**反而掩盖真实的运行失败**。先定性、再动手，比"看着像就改"重要。

## 结论一句话（修正后）

8 个失败里**没有一个是产品功能性 bug 的直接证据**：**4 个环境噪声**（R04–R07）、1 个断言过窄（S03）、1 个预算口径可疑（R01）、2 个待人工读输出（T03/V01）。

但也不要过度乐观：**恢复能力（Failure Recovery）的真实水平仍未测出**——4 个环境噪声刚好落在 recovery 层，所以「2/7」这个数字目前不可信，需在网络正常时重跑该子集。

## 2026-11-09 复跑：恢复能力真实水平 = **1/7**，且原因是产品行为

网络恢复后跑了 recovery 子集（`--only recovery`，7 条，**28 次模型调用 / 84,817 tokens**）：

```
RESULTS: 1/7 pass (14.3%)
  Failed: R01, R02, R03, R04, R05, R06   （仅 R07 通过）
  对比 11-04：new fail=[R02, R03]  new pass=[R07]  still fail=[R01, R04, R05, R06]
```

**上次的 `Connection error.` 确实是环境噪声**（这次同一条用例真的跑起来了，错误变成注入的 `injected fault (eval)`）。所以 11-04 那四条的环境噪声判断成立。

但复跑暴露了**真实的恢复能力缺陷**，而且模式统一 —— **同一个失败的工具被反复重试到轮次上限**：

| 用例 | 注入故障 | 实际行为 | 判定 |
|---|---|---|---|
| R01 | `read_file=error` | `read_file` 重试 **5 次**（中间只夹了一次 `list_directory`） | tools/answer/budget 三连挂 |
| R04 | `research/fetch_url=error` | `research` 4 次 + `fetch_url` 1 次 | tools/answer |
| R05 | `see_screen=error` | `see_screen` **3 次**，最后回答未覆盖"没看成"要点 | answer |
| R06 | `read_file=empty` | 换着读 README / README.en / CLAUDE.md / AGENTS.md（空结果 ×4） | tools/answer |
| R07 | `fetch_url=timeout` | 超时 2 次后**如实说明** → **通过** | ✅ |

**归纳**：这不是"评测不成熟"，而是 **agent 缺少"放弃策略"**——工具连续失败后，它不会停下来换方案或如实报告，而是把同一调用重试到 `max_tool_rounds`（5）耗尽；R07 之所以过，正是因为它在第 2 次超时后放弃了。

**两条附带发现**：

1. **用例级不稳定**：R02/R03 在 11-04 通过、这次失败（R07 反之）。恢复类用例依赖模型判断，单次通过/失败不足以定论；比较时至少要跑两遍或看多次趋势。
2. **`tools` 断言对"重试"过于敏感**：R01/R04/R06 的 `tools` 挂，本质是"重试次数多"，而非"选错工具"。修复方向不在放宽断言，而在产品侧止血。

## 横向结论

1. **R04–R07 同因但不是代码问题**：同一轮网络抖动连续打断四个用例；改 harness 是错的。
2. **恢复能力已测出：1/7**，根因是"连续失败后不放弃、重试到轮次上限"，属产品行为而非评测缺陷；`R07` 证明了正确路径（两次超时后如实报告即通过），可以直接作为 prompt 的正面样例。
3. **可复现性风险**：这轮跑在 11-04（当时网络可用）。本机 SOCKS 代理（`127.0.0.1:7890`）一度不可用；recovery / 搜索类用例依赖网络，**网络条件不同则失败集不同**，对比基线前必须确认网络一致。

## 待定：基础设施失败应与行为失败分开记账（只建议，未实施）

即便是真实网络错误，把整个 case 判成 `run` 失败也会污染质量信号。按 ADR-0012 的精神，基础设施失败应当单独标记（例如 `not_run` / `infra_error`）并在汇总里单列，**不进通过率分母**。

这会扩大 eval 的判定语义（新增一种"没跑成"的状态），超出"修 R04–R07"的范围，因此本轮未做。要做得单独立项（改 ADR-0012 或加一条）。

| 用例 | 检查项 | 实际回答 | 修正后归类 |
|---|---|---|---|
| R01 | tools, answer, **budget** | **空**（5 轮耗尽后没有收尾） | 产品：不放弃 + **轮次耗尽无收尾** |
| R02 | answer | 「好的，那我就不写了。如果你改主意了，随时跟我说～」 | **断言过窄**（关键词要 `未写入`/`没有执行`，但没有等价说法） |
| R03 | tools | （answer 通过） | 产品：熔断后仍换工具硬试 |
| R04 | tools, answer | — | 产品：不放弃 |
| R05 | answer | 「工具好像有点抽风，试了几次都没抓到画面…我换个方式帮你」 | **断言过窄**（关键词要 `没看成`/`看不到`，缺"没抓到"） |
| R06 | tools, answer | — | 产品：不放弃 |
| R07 | — | 超时两次后如实说明 | 正面样例 |

**最终结构：4 个"不放弃"（R01/R03/R04/R06）+ 2 个 `answer` 断言过窄（R02/R05）+ 1 个正面样例（R07）。**

### 两条方法教训（比具体用例更重要）

1. **"空输出"不是证据**。`max_tokens=60` + 推理模型会稳定制造空串：同一 prompt 不带图也空，预算给到 1500 才说话（V01 那轮实测）。判断"模型能不能看图"必须看**明确拒绝**，不能看空串。
2. **`answer` 关键词断言是系统性风险**。recovery 层的关键词表按字面写（`未写入`/`没看成`），而模型会说「我就不写了」「没抓到画面」——**语义对、字面不对**。这类假红会让任何用例的 `answer` 都可能误判；修法是把关键词放宽到等价说法，或改成语义判定。目前 `max_tokens` 在 agent 链路是 4096（`llm_service`），**不是**截断造成的，所以这是纯断言问题。

## 为什么这张表要入库

`backend/eval_results.md` 是每次跑都会变的生成物，故意不入库。但它是这张表唯一的依据——若不把判断固化下来，将来没人能追溯"8 条失败为什么这样归类"。所以本文件入库，并在 `docs/STATE.md` §4 引用。
