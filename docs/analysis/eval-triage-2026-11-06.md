## 结论一句话

**8 个失败里没有一个是"产品功能性 bug"的直接证据**：4 个疑似 harness 判定错、1 个疑似预算断言口径、1 个确认断言过窄、2 个待人工读实际输出。真正的信号是「Failure Recovery 2/7」这个比例——但它更可能反映 **eval 自身不成熟**，而不是恢复能力差。

## 逐条归类

| 失败项 | 类别 | 依据 | 建议动作 | 优先级 |
|---|---|---|---|---|
| **R04** | 判定/断言问题（大可能） | 与 R05–R07 同为 `run, tools, answer` 三连挂；trace 位置对应 `⚠️ Error: Connection error.` | 先确认该错误是**注入的**还是真实网络；若是注入 → 修 runner：注入故障只应影响"是否恢复"的断言，不应把 run 判负 | 高（四例同因） |
| **R05** | 同上 | 同上；`⚠️ Error: Request timed out.` | 与 R04 一并修 | 高 |
| **R06** | 同上 | 同上；`Connection error.` | 同上 | 高 |
| **R07** | 同上 | 同上 | 同上 | 高 |
| **R01** | 断言口径可疑 | 唯一挂了 `budget` 的用例（`tools/answer/budget`）；recovery 场景含重试轮次，预算断言可能把重试算进角色消息数 | 看 `budget` 断言取的是哪一层计数；若把重试计入则改断言 | 中 |

## 三条横向结论

1. **R04–R07 同因**：一次修复可能同时解决四例，是投入产出比最高的一项。
2. **最该先改的是 harness，不是产品代码**：把"注入的故障"当作 run 失败，会让整层 recovery 评测失去意义。
3. **可复现性风险**：这轮跑在 11-04（当时网络可用）。本机 SOCKS 代理（`127.0.0.1:7890`）现在不可用；recovery / 搜索类用例依赖网络，**代理不恢复的话重跑会得到不同的失败集**，对比基线时要注意。

`backend/eval_results.md` 是每次跑都会变的生成物，故意不入库。但它是这张表唯一的依据——若不把判断固化下来，将来没人能追溯"8 条失败为什么这样归类"。所以本文件入库，并在 `docs/STATE.md` §4 引用。
