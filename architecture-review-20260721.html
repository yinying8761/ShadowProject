候选方案 #1

拆分 WebSocket 处理器上帝模块

强烈推荐
backend/api/chat.py 754 行

🔴 问题

chat.py 是一个浅层模块，其庞大的实现背后本质上只有一个入口点 （handle_message）。它承载了 8 个以上不同的关注点：

  • WebSocket 生命周期（连接/断开/重连）
  • 主动陪伴监控器状态管理（5 个回调、刷新循环）
  • 每日问候编排（位置 → 天气 → 记忆 → LLM → 持久化）
  • 位置更新处理（浏览器定位 → 逆地理编码 → 天气 → 缓存）
  • 搜索路由器集成（意图检测 → 缓存 → 增强）
  • POI/美食推荐注入
  • 屏幕截图（指纹去重 + 权限审批）
  • 工具审批流程（pending future、超时处理）

自 0e2165c 提交以来的每个功能都落入了这个文件。零局部性—— 修改屏幕截图的工作方式需要编辑与修改每日问候相同的文件。

🟢 解决方案

将每个关注点提取到独立的深层模块中，每个模块在干净的接缝处拥有窄接口。 WebSocket 处理器变成一个薄适配器，将它们连接在一起。

GreetingOrchestrator（问候编排器） — 接收 (character_id, conversation_id, cached_location) → 产出问候 token。接口：单一方法 run(params) → AsyncIterator[event]。
ProactiveSession（主动会话） — 用 WebSocket 专用回调包装 ProactiveWatcher。接收注入的 send_json 函数。
ScreenCaptureGate（屏幕捕获门） — 指纹去重 + 权限审批。接口：try_capture(focus?) → str | None。
MessageAugmenter（消息增强器） — 流水线：路由 → 美食/POI → 屏幕。接口：augment(content) → str。

候选方案 #2

通过参数化统一 Agent.run() 和 run_daily_greeting()

强烈推荐
backend/core/agent.py 约 200 行重复逻辑

🔴 问题

run() 和 run_daily_greeting() 几乎是相同的副本： 都加载角色、构建系统提示词、从 LLM 流式获取、持久化消息。 run_daily_greeting 是通过复制 run 并移除工具执行而创建的。

添加新的 LLM 事件类型或更改消息持久化流程需要同时修改两个方法。 在一个方法中添加的每个功能都是另一个方法中的潜在 bug。

🟢 解决方案

用 mode 参数化 run()，控制工具可用性、最大轮次和后处理。 run_daily_greeting 变成一个薄调用者： 

await agent.run(
  session=session,
  user_message=None,
  conversation_id=cid,
  character_id=cid,
  mode="greeting",  // 禁用工具，注入问候提示词
  extra_context={
    "location": location_info,
    "weather": weather_info,
    "days_since_last": days,
    "memories": memory_texts,
  },
)

候选方案 #3

拆分 chatStore：领域状态 vs. 通信管道

值得探索
frontend/src/stores/chatStore.ts 168 行，20+ 个字段

🔴 问题

chatStore 是一个浅层模块，其接口几乎与实现一样复杂。 它混合了三个不同的关注点：

  • 领域状态：消息、流式内容、对话 ID
  • 通信桥接：wsSendMessage、wsSendJson、wsSendApprovalResponse——由 WebSocket hook 注入
  • 功能回调：speakMessage、stopSpeaking——由 TTS hook 注入

添加新的通信通道（例如「发送在线状态」）意味着需要再添加一个字段和 setter。 每个需要与 WebSocket 通信的 hook 都必须轮询 store——这是一种脆弱的隐式依赖。

🟢 解决方案

创建一个 WebSocketBus 模块——一个响应式事件发射器，hook 直接订阅它， 而不通过 store。store 缩减为纯粹的领域状态。

// 新增：WebSocketBus（单一接缝）
const bus = createWebSocketBus(url)
bus.send({ type: 'daily_greeting' })
bus.on('token', (data) => { ... })
// chatStore 缩减为：
messages, isStreaming, streamingContent,
conversationId, pendingApproval

候选方案 #4

拆分 MemoryService：存储适配器 vs. 检索逻辑

值得探索
backend/services/memory_service.py 510 行，10+ 个公开方法

🔴 问题

MemoryService 在一个模块中混合了三层关注点：

  • 存储：FTS5 虚拟表、触发器、二进制 embedding 打包/解包、CRUD
  • 检索：混合搜索流水线（FTS5 排名 → embedding 余弦相似度 → RRF 合并 → 重要性/时效性加权）
  • 编排：LLM 提取、去重、剪枝、通知队列

接口是浅层的——调用者必须了解 _ensure_fts5()（模块级函数）、 push/pop_memory_notifications（也是模块级函数）以及单例 memory_service。 真正的接缝（切换存储或排序算法的地方）并不存在。

🟢 解决方案

拆分为三个模块，每个模块有自己的接缝：

MemoryStore（存储适配器） — 接口：add()、delete()、search_fts(query)、get_batch(ids)。目前有一个适配器（SQLite+FTS5），但接缝已为未来的向量数据库做好准备。
MemoryRetriever（检索器） — 接口：search(query, character_id, top_k) → list[Memory]。隐藏 RRF、余弦相似度、重要性/时效性逻辑。
MemoryExtractor（提取器） — 接口：extract(conversation_id, messages) → list[Memory]。LLM 调用 + 去重 + 存储。

候选方案 #5

将 ToolRegistry 改为可注入，而非模块级单例

值得探索
backend/core/tool_registry.py backend/main.py

🔴 问题

tool_registry = ToolRegistry() 在模块加载时创建，register_tools() 在任何测试运行之前在 main.py 中被调用。这是可变全局状态—— 每个测试共享同一个注册表。Agent 直接从模块导入它， 因此测试无法注册假工具。

删除测试：如果删除全局 tool_registry，复杂性会 集中到 Agent 构造函数中（它将作为依赖项接收）。这是一件好事。

🟢 解决方案

将 tool_registry 作为构造函数依赖项传递给 Agent。 main.py 创建真实的注册表；测试创建假的。

// 改造前：
class Agent:
def __init__(self):
from core.tool_registry import tool_registry
self.tool_registry = tool_registry
// 改造后：
class Agent:
def __init__(self, tool_registry=None):
self.tool_registry = tool_registry or ToolRegistry()

🔗 局部性

工具注册的知识保留在 main.py 中。Agent 不关心工具来自哪里。

⚡ 杠杆效应

同一个 Agent 可以使用真实工具、假工具或受限工具集运行——用于测试或不同模式（例如问候模式 = 无工具）。

🧪 可测试性

测试通过 register("fake_tool", handler=mock) 注入注册表。无需重置全局状态。

候选方案 #6

从 LLMService 中提取消息格式转换逻辑

探索性
backend/services/llm_service.py 215 行

🔴 问题

内部格式到提供商格式的消息转换在 _stream_openai、 _stream_anthropic 和 chat_sync 中重复出现。添加第三个提供商（如 Google Gemini） 意味着第三次复制格式逻辑。

目前，这是一个单适配器接缝（一个内部格式 → OpenAI 或 Anthropic）。 由于项目已支持两个提供商，这个接缝是真实的，应该有自己独立的模块。

🟢 解决方案

每个提供商对应一个 MessageFormatter 模块。LLMService.stream_chat 将格式转换委托给格式化器，然后从提供商流式获取。

class MessageFormatter:
def to_provider(messages) → ProviderMessages
def from_provider_stream(chunk) → Event
// 每个提供商一个适配器：
OpenAIFormatter, AnthropicFormatter, ...

🔗 局部性

添加新提供商 = 一个包含格式逻辑的新文件。LLMService 不再变更。

⚡ 杠杆效应

formatter.to_provider(msg)——一个调用点，隐藏了所有格式转换的复杂性。

🧪 可测试性

独立测试每个格式化器——给它消息，检查输出格式。不需要真正的 LLM 调用。

首要推荐

从候选方案 #1：拆分 WebSocket 处理器开始。这个文件在每个提交中都有改动， 局部性最差，是代码库中最浅层的模块。建议执行顺序如下：
